# Aevia 性能剖析

在仓库根目录运行：

```powershell
npm.cmd run test:profile
npm.cmd run test:profile -- --set=smoke --case=render-dirty --collector=all
npm.cmd run test:profile -- --case=draw-dense --collector=all
npm.cmd run test:profile -- --compare=<previous-manifest>
```

`core` 覆盖 1 万、5 万、10 万点进房，三种重绘路径和双端同区绘制。`all` 再加入空房、分散绘制、单端绘制、换页、撤销重做和刷新。指定 `--case` 时只跑对应场景。正常对照和阶段计时使用 1 次预热、5 次正式样本，其他采集各取一个诊断窗口。结果和原始数据在 `tests/reports/profile/<run-id>`。

`--case=brushes --collector=spans` 采集 1 万点铅笔与荧光笔的独立全量绘制，并以完整重绘像素作为检查。该样例用于区分工具渲染成本，不覆盖实时输入或协作。

`--case=pending-store --collector=baseline` 隔离测量 IndexedDB 中 100 条待确认操作的批量写入、按序读取与删除，并检查内容、顺序及删除结果。运行 `f2297de6-0d9f-4d05-8c31-196626c8ff12` 的五个样本中位数分别为 5.18、3.13、10.25 ms；记录是仅含序号的小对象，不代表真实大型操作或端到端耗时。它不模拟浏览器崩溃，也不证明离线编辑可恢复：当前传输层在 WebSocket 未打开时直接拒绝发送，新操作不会走入该待确认队列。

`--case=pending-store-points` 使用 100 条、每条带 75 个合成点的记录。运行 `2244def5-32c3-48c5-8b0f-89f7b432ed89` 的五个样本中位数分别为写入 6.24、读取 8.94、删除 15.15 ms；该对象只是点数据规模近似，并非完整协议操作。

`--case=text-tools --collector=spans` 分别创建文字和便签，记录编辑框打开、输入、提交到编辑框关闭及内容被观察到的耗时，并与新加入客户端的画布对照。文字编辑可能实时同步，提交之前内容已可见时，该指标包含编辑框关闭和截图观察时间。

`--case=transport-pair --collector=baseline` 先在两端初始化结束后使用相同的鼠标轨迹并画，再分别记录实际通过 Ring 和 transferable 的批次数。transferable 组通过测试页面启动脚本屏蔽 SharedArrayBuffer，不改变产品代码；两组截取 Worker 消息类型计数，并校验两端与新加入客户端的画布。轨迹相同但浏览器可能合并输入，需同时比较操作量。采用分组执行，样本还受运行顺序和机器状态影响。

`--case=clear-undo --collector=spans` 用两个客户端分别绘制，然后通过界面清屏、刷新并撤销清屏。逐端检查两块笔迹区域的空白和恢复，分别记录滑动、服务端确认和四处截图观察时间。截图观察包含采集和轮询成本，不直接代表内部清屏执行时间。截图中包含远端光标，观察前将两端光标移出待检查区域；之前约 10 秒的结果中，远端光标停在本地的第二个待测区域，移动光标后同样本地观察约 185 ms，支持光标影响了截图判断，但不能推广为所有场景的结论。

基准运行 `d43e6c58-83cb-4db8-a4dc-8ee301a954a5` 在小画布场景完成五个正式样本；松开清屏滑块到两端区域均被观察为空白的中位数为 207 ms，撤销后到两端区域均被观察到内容为 162 ms。两者都包含截图采样和轮询，不能视作渲染本身耗时，也不能推广到大房间。

`--case=delta-reconnect --collector=baseline` 建立已有房间序号后断开一端连接，由另一端写入新笔迹，再恢复网络，要求看到 delta-replay 的开始与结束消息以及目标区域的新笔迹。首次完整断线冒烟 `f506de04-3a99-4fc4-89b5-4d07cda9636d` 收到了补发消息但目标区域等待超时。经三端对照及代码排查，服务端重发 JSON 时遗漏 pushType，修复后该场景 `548a6d5b-51b4-4942-8cf0-ff479b778e8d` 通过；仅覆盖本机一次断线补发。

- `baseline` 用优化后的前端构建和独立临时环境测量像素及公开协议。`spans` 额外启用诊断 Vite 插件和 Go overlay。正式构建入口与协议保持原样。
- `--case=decision --collector=spans` 同时执行十万点进房和初始化期间／完成后两组密集绘制。`--case=dense-pair` 只执行后两组。两组使用 Lab 初始化完成信号；测试构建移除 Lab 对实时操作的额外强制重绘。鼠标事件以相同节奏送入，但浏览器合并输入可能造成操作数不同，需同时检查确认数、轨迹和图元数量。
- `--case=join-contention --collector=baseline` 比较十万点进房时无输入和输入五条笔迹。输入组等待页面处理初始化元信息，并检查首次输入开始早于 Worker 初始化完成、服务端没有拒绝操作、最终画面与新加入客户端对照。该场景启用 Lab 初始化标记，画面稳定时间包含新增笔迹的绘制；输入可能跨越初始化完成时刻，两组按顺序运行，不能仅凭差值认定初始化计算的因果开销。`d563c6f1-66ac-4306-8be6-4e6a526fc9b8` 中两组各五个样本的稳定时间中位数分别约 1061 和 1143 ms；范围分别为 1021–1349 和 1025–1244 ms。
- 元信息就绪前输入的试验 `d8d79687-8126-4628-a37e-a2b70c33354d` 中，服务端返回 `INVALID_SCENE_OPERATION`，原因是操作身份与房间会话不匹配。消息顺序显示至少一笔提交早于 `init-meta`；当前 `handleInitMeta` 才设置画布的 `userId` 和 `roomId`。该问题应与性能对照分开处理：禁止首屏就绪前的编辑需要覆盖画布、工具栏及键盘入口，并以 Worker 完成初始化为依据；不能等待后台全量历史补载，也不能仅依赖固定延时。
- `--case=join-gate --collector=baseline` 在测试页面中将 Worker 的初始化屏障延迟 1.5 秒，以便稳定检查加载期间的绘制和撤销快捷键不会提交操作；解禁后检查笔迹得到服务端接受并与新客户端的整体画面对照。该延迟仅用于此功能测试，不可用于衡量正常进房性能。
- 首屏门禁接入后，`join-100k-active` 的画布输入会被阻止；若没有提交操作，该样本应判为无效。之前的对照是在门禁接入前采集的，不能直接用当前代码重复该对照并声称工作量相同。需要无门禁对照时，应使用明确记录版本的旧构建或隔离的测试配置。
- `cpu` 用 Chromium 的 V8 采样按目标生成 Bottom-up，Go 通过本机 pprof 输出 CPU 排行。`timeline` 生成 Chromium 和 Go 时间线。`memory` 记录页面 isolate 的堆用量和 Go 分配剖面。跨进程校准记录原始时钟往返，以误差区间解释 Worker 队列等待。
- 页面和 Worker 的统计按目标分开。阶段累计值有嵌套和重叠，不能直接累加为总延迟。Worker 确认与实际像素变化是独立证据。密集用例的重放比较包括新观察端初始化。
- 重绘隔离样例将局部笔迹完整包在重绘区内，样例准备、绘制和像素校验在同一次浏览器调用中完成。独立计时只量目标调用，CPU 采样窗口包含准备阶段。此前冒烟中，裁剪边界与笔迹相交，以及将局部重绘拆到后续浏览器调用时，逐像素对照均发现差异，分别见报告 `5f057319-69a8-49c3-93d8-4293eec132d1` 和 `c7cd7da8-274f-4500-92ec-629bf59fe09b`。
- 动作、模块和验证方式记录在每次清单。待补覆盖包括大房间清屏撤销、增量重连、IndexedDB 断线写入恢复、权限与账号流、文字和便签的并发编辑、完整工具矩阵，以及单笔操作跨 Go、Worker 和像素的完整依赖图。
- 使用 `go test ./internal/room ./internal/storage -run '^$' -bench '^BenchmarkProfile' -benchtime=200ms -count=3` 从 Go 模块测索引与 SQLite。索引使用旧格式合成点以单独量化点索引。SQLite 测反复更新同一批记录的事务成本。

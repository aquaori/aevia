# Aevia S00～S08 开发过程说明

本文按实际提交记录解释这一轮白板开发做了什么。它是一份面向首次接触项目的阅读指南：先介绍基本概念，再按阶段解释每个功能提交。提交号是 Git 中用来查找一次代码变更的短编号。

本文以本分支当前代码为准。提交记录代表代码曾被加入，不等于所有设备、所有场景都已经人工验收。部分开发分支的提交后来经过 cherry-pick 或 squash 合并，所以同一项改动可能还有另一个提交号；下文以阶段集成分支的提交为主，避免把同一份工作算两次。CI 和文档维护的关联提交也会说明。

## 先认识几个概念

Aevia 是多人协作白板。浏览器负责接收鼠标或手写笔输入、展示画面；Go 后端负责房间、账户、同步和持久保存；SQLite 是目前使用的本地数据库。多人看到相同内容，需要把每次画笔、移动、擦除等行为作为操作发送给后端，再分发给其他参与者。

**Scene Engine（场景引擎）**是白板内部维护内容的部分：它根据操作记录计算当前有哪些元素、它们的位置和显示顺序，并回答“鼠标点中了什么”等问题。**Canvas** 是浏览器提供的画布，负责把结果画成像素。**Worker** 是浏览器提供的后台线程，可以把较重的计算和绘制从网页主线程移开。二者之间传消息并不等于画面已经显示完成。

**撤回和重做**控制自己的历史操作是否生效；先撤回再新画一笔时，旧的重做分支应该失效。**快照**可以理解为某个时刻的数据副本；**重放**是根据保存的操作重新计算画面；**增量更新**是只处理发生变化的部分。**CI** 是提交或 PR 后自动运行的检查，PR 是把一个开发分支的改动申请合并到主分支的方式。

## S00：记录问题和基线

- `499474c`「记录 S00 复现基线」：把十个走查问题和三项新需求整理成可重复的步骤与预期，覆盖选区、撤回重做、笔迹、文字和便签。文档在 `docs/scene-s00-regressions.md`。它帮助后续讨论时区分“需要达到的结果”和“已经通过的检查”。

## S01～S03：白板交互、工具效果和文字便签

这三个阶段的主要实现集中在同一项功能提交中，并非每个阶段都有独立提交。目标是让已有白板更好用，而不是另起一个新白板。

- `3002d84`「完善交互工具和文字编辑」：调整选区命中、拖动、旋转及画面更新；修正撤回后新编辑应放弃旧重做分支的处理；补充双线、铅笔和 Shift 等比图形；把文字编辑放到画布内，改善换行与文字、便签编辑和最终显示之间的一致性。也同步调整前后端数据类型与相关检查。
- `4c2c2ac`「恢复缓存页面的历史回放」：切换到缓存过的页面时，重新应用场景操作，避免旧笔迹或历史状态没有正确恢复。
- `90d157e`「避免文字选区控制点重复」：调整文字编辑与普通选区的交接，减少控制柄重复显示。
- `dd8e094`「统一便签圆角样式」：调整画布中便签的边角，使其更接近编辑时的外观。
- `4f06325`「重置中断的文字输入状态」：处理输入法组合输入中断，避免之后继续编辑时沿用失效的组合状态。
- `23f3953`（PR #23）：将这一组编辑器改进汇总合入主分支；这是合并结果，不代表又重新实现了一次。
- `123db79`「细化绘制、文字和擦除」：继续修正笔迹与文本显示、擦除范围及相关数据处理。
- `46bb31c`「拖动预览保留擦除缺口」：被部分擦除的笔迹在框选拖动时，预览也保留已经擦掉的区域，避免拖动途中暂时恢复成完整笔迹。

期间的 `bb1663a`、`7c6e413`、`7faa4b2`、`9fa0764` 分别调整不同 Git 事件触发的 CI、移除重复 PR 检查、更新说明和检查工作流配置。这些提交改善检查流程，不属于新的白板工具。

## S04：多人协作与故障恢复

这一阶段主要解决“断线、切页或保存失败时，画面和已保存内容怎样保持一致”。例如，用户切换页面的同时另一位用户画了一笔，页面快照不能把那笔后到的操作覆盖掉。

- `24fb87a`：恢复页面时保留同时到达的实时操作，并按操作编号去重。
- `4a9fda0`：等待 Worker 完成场景初始化后才推进恢复位置，避免客户端误以为尚未处理的操作已经恢复。
- `b7467c8`：房间进入只读状态而写入被拒绝时，返回被拒绝的操作编号，方便客户端知道哪一笔没有保存。
- `07c4314`：记录隔离环境下的大场景容量诊断。该记录是指定机器和环境的一次观察，不是所有机器的容量保证。
- `0ecf053`：整理恢复边界与相关检查，形成 `docs/scene-s04-reliability.md`。
- `d67304e`：发现页面恢复数据不完整时不把它当作成功完成，避免在缺失数据的画面上继续工作。
- `f0cc029`：补充数据库写满、锁竞争等存储失败边界的测试。
- `655e677`：页面加载期间保留本地尚未确认的写入，避免加载过程把它们丢掉。
- `d19f484`：处理初始化数据流中断或不完整的情况，触发恢复而不是停在假完成状态。
- `e884e3e`：Worker 异常时停止不安全的续传，并给出恢复提示。
- PR #25 将 S04 合并到主分支。内存中的待发送操作不等于持久离线日志；关闭浏览器后尚未保存的内容仍有丢失风险。

## S05：账户、房间和成员管理

S05 将此前较简单的临时房间入口扩展为账户与房间工作台。账户用于识别长期用户；游客不需要账户；房间角色决定谁能编辑或只读。

- `1a1956b`：加入用户名密码注册、登录和独立昵称，以及账户会话。
- `6d845cd`：建立账户与房间的归属、成员关系和房间列表；加入房间后可以再次从列表进入。
- `6eb58e7`：增加房间设置、成员角色及相关后端权限检查。
- `30b2d20`：支持邀请链接设置有效期和撤销，分享入口与房间访问规则相连。
- `a598f54`：加入房主转让请求和同账号跨设备进入同一房间时的接替逻辑。
- `bc2a84b`：补充游客权限、踢出和协作连接处理。
- `464b693`：把页面切换、角色变化和房间界面联动起来。
- `891a222`：检查同一账号由另一设备接替后，自己的历史操作仍可使用。
- `7dc93e4`：检查只读游客不能执行编辑操作。
- `5fdd457`：在白板房间内部增加房间设置入口，减少必须返回首页才能管理的情况。
- `46b7f35`：重新设计房间入口、邀请和管理界面，并区分游客与登录用户的入口体验。
- `1896feb`：修正账户机制下外部测试驱动创建房间的流程。
- `be84b82`：完善房间准入、一次性连接票据、账户会话与读取快照的隔离处理。
- PR #27 将 S05 合入主分支。生产环境是否创建系统默认房间取决于配置；旧进程如果没有重启，可能仍返回旧接口占位错误。

## S06：把计算和绘制分开

以前场景计算与 Canvas 绘制结合较紧。S06 的方向是继续使用 TypeScript，把“计算白板内容”和“把结果画出来”拆成不同职责，为后续优化留出清晰边界。它没有进行 Rust 迁移。

- `6bf8301`：抽出 `SceneCore`，让操作折叠、查询等场景计算不依赖 Canvas，并提供可读取的渲染快照。
- `3523091`：让 Canvas 绘制器消费场景渲染数据，补充资源标识和渲染数据编解码。
- `c0efe89`：隔离过期 Worker 响应，初始化 Worker 或转移画布失败时提供可用回退。
- `020426a`：分别记录接收、场景处理和绘制进度，避免把“消息已收到”误认为“用户已经看到”。
- `5003376`：Worker 在画布转移后出错时，尝试重建画布并重新同步未确认操作。
- `9c76c4d`：支持从 Worker 按需读取完整渲染快照或差量。
- `a83c7a8`：保持绘制、场景操作与查询消息的先后顺序，并暴露队列状态。
- `9b0c61b`：将 S05 已合入的主分支同步到 S06，保留只读权限和画布恢复两边的逻辑。
- `2001a3e`（PR #28）：S06 合并到主分支的结果。渲染数据的按需导出路径与正式绘制路径不同，不应把它称为已经完成全部性能优化。

## S07：暂缓的方向

原排期中的 S07 是 Rust/WASM 场景核心迁移。用户尚未决定是否投入，因此本轮没有实施。S08 改为继续在现有 TypeScript 场景核心上进行，不依赖 S07。

## S08：增量更新和调度

S08 希望减少“改动一小块内容却处理很多内容”的情况，也希望较大的任务能够分段执行。**局部更新**只关注受影响的元素或画布区域；**分片调度**把任务拆成若干小段，让浏览器有机会处理其他工作。

- `10801bb`：记录受影响元素并生成渲染差量；优化正常追加笔迹时的脏区计算；合并连续绘制区域；对初始化和点批次作分片处理；改善迟到操作的排序和历史组定位；减少不必要的索引整理扫描。
- `edd13c6`：继续将场景回放、历史重建、排序和索引整理拆成步骤；独立场景投影可以在片段间让出 Worker；增加大型历史组的针对性检查。该提交也曾加入 `predict=1` 的浏览器轨迹预测实验；用户实际体验后决定移除，最终版本不保留此实验。
- `e66dbfa`：移除轨迹预测实验，并修正局部重绘导致笔迹出现细缝的问题；同时写下本文的第一版。
- `70ba5ac`：缓存元素边界，减少重复遍历长笔迹；将单条长笔迹操作继续拆成小段，避免一条操作把外层分片变成一次长任务；并调整后台投影的执行机会。
- `0feebc7`：记录新生成的笔迹图元，使长笔迹追加和结束时只需发送新部分；加入大批乱序数据分片排序的检查。
- `67d43b8`：补充阶段说明和项目内部的场景调度说明，帮助后来维护代码的人了解上述结构。
- `557477b`：同步已经包含 S06 的主分支，属于集成提交，不是独立功能。

当前边界：独立投影可与活动场景工作交替；活动场景的大型事务在分片之间让出线程，但依赖同一场景状态的后续操作仍需按顺序等待。不能因此声称所有交互都有低延迟，也没有证据表明十万点性能已经恢复到旧版本水平。共享内存 Ring、Rust/WASM 和 WebGPU 均不属于本次 S08 的已实现结果。

## 如何看检查结果和后续事项

本阶段运行过相关场景单元测试、Worker 浏览器用例、前端构建和提交时的快速检查。这些检查能说明对应样例通过，不能替代真实鼠标、手写笔、不同浏览器和多人房间中的持续走查。实际体验中发现的新问题应记录复现步骤，修复后再核对；不要只凭提交数量或一次测试通过判断整个产品已经完工。

后续方向按先前讨论，包括继续改进调度和内存、评估批量传输与共享 Ring。Rust 和 WebGPU 仍是待验证收益后再决定的可选方向。用户实际试用后发现绘制时当前笔迹和经过的旧笔迹可能出现白色间隙。文档初稿完成后排查发现，局部重绘清除的范围比查找待重画内容的范围更大，且边界可能落在半个设备像素；现已统一清除、裁剪和查找范围并对齐设备像素。新增浏览器用例覆盖粗笔迹上的反复局部重绘；用户实际绘制效果仍待走查。

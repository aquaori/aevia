# Aevia S00～S08 开发过程说明

本文按实际提交记录解释这一轮白板开发做了什么。它是一份面向首次接触项目的阅读指南：先介绍基本概念，再按阶段解释每个功能提交。提交号是 Git 中用来查找一次代码变更的短编号。

本文以本分支当前代码为准。提交记录代表代码曾被加入，不等于所有设备、所有场景都已经人工验收。部分开发分支的提交后来经过 cherry-pick 或 squash 合并，所以同一项改动可能还有另一个提交号；下文以阶段集成分支的提交为主，避免把同一份工作算两次。CI 和文档维护的关联提交也会说明。

## 先认识几个概念

Aevia 是多人协作白板。浏览器负责接收鼠标或手写笔输入、展示画面；Go 后端负责房间、账户、同步和持久保存；SQLite 是目前使用的本地数据库。多人看到相同内容，需要把每次画笔、移动、擦除等行为作为操作发送给后端，再分发给其他参与者。

**Scene Engine（场景引擎）**是白板内部维护内容的部分：它根据操作记录计算当前有哪些元素、它们的位置和显示顺序，并回答“鼠标点中了什么”等问题。**Canvas** 是浏览器提供的画布，负责把结果画成像素。**Worker** 是浏览器提供的后台线程，可以把较重的计算和绘制从网页主线程移开。二者之间传消息并不等于画面已经显示完成。

**撤回和重做**控制自己的历史操作是否生效；先撤回再新画一笔时，旧的重做分支应该失效。**快照**可以理解为某个时刻的数据副本；**重放**是根据保存的操作重新计算画面；**增量更新**是只处理发生变化的部分。**CI** 是提交或 PR 后自动运行的检查，PR 是把一个开发分支的改动申请合并到主分支的方式。

## S08：增量更新和调度

S08 希望减少“改动一小块内容却处理很多内容”的情况，也希望较大的任务能够分段执行。**局部更新**只关注受影响的元素或画布区域；**分片调度**把任务拆成若干小段，让浏览器有机会处理其他工作。

- `10801bb`：记录受影响元素并生成渲染差量；优化正常追加笔迹时的脏区计算；合并连续绘制区域；对初始化和点批次作分片处理；改善迟到操作的排序和历史组定位；减少不必要的索引整理扫描。
- `edd13c6`：继续将场景回放、历史重建、排序和索引整理拆成步骤；独立场景投影可以在片段间让出 Worker；增加大型历史组的针对性检查。该提交也曾加入 `predict=1` 的浏览器轨迹预测实验；用户实际体验后决定移除，最终版本不保留此实验。
- `e66dbfa`：移除轨迹预测实验，并修正局部重绘导致笔迹出现细缝的问题；同时写下本文的第一版。
- `70ba5ac`：缓存元素边界，减少重复遍历长笔迹；将单条长笔迹操作继续拆成小段，避免一条操作把外层分片变成一次长任务；并调整后台投影的执行机会。
- `0feebc7`：记录新生成的笔迹图元，使长笔迹追加和结束时只需发送新部分；加入大批乱序数据分片排序的检查。
- `67d43b8`：补充阶段说明和项目内部的场景调度说明，帮助后来维护代码的人了解上述结构。
- `557477b`：同步已经包含 S06 的主分支，属于集成提交，不是独立功能。

当前边界：独立投影可与活动场景工作交替；活动场景的大型事务在分片之间让出线程，但依赖同一场景状态的后续操作仍需按顺序等待。不能因此声称所有交互都有低延迟，也没有证据表明十万点性能已经恢复到旧版本水平。共享内存 Ring、Rust/WASM 和 WebGPU 均不属于本次 S08 的已实现结果。

## 如何看检查结果和后续事项

本阶段运行过相关场景单元测试、Worker 浏览器用例、前端构建和提交时的快速检查。这些检查能说明对应样例通过，不能替代真实鼠标、手写笔、不同浏览器和多人房间中的持续走查。实际体验中发现的新问题应记录复现步骤，修复后再核对；不要只凭提交数量或一次测试通过判断整个产品已经完工。

后续方向按先前讨论，包括继续改进调度和内存、评估批量传输与共享 Ring。Rust 和 WebGPU 仍是待验证收益后再决定的可选方向。用户实际试用后发现绘制时当前笔迹和经过的旧笔迹可能出现白色间隙。文档初稿完成后排查发现，局部重绘清除的范围比查找待重画内容的范围更大，且边界可能落在半个设备像素；现已统一清除、裁剪和查找范围并对齐设备像素。新增浏览器用例覆盖粗笔迹上的反复局部重绘；用户实际绘制效果仍待走查。

# 进一步理解：一次操作从鼠标走到其他人的屏幕

先拿“在房间中画一条线”举例。浏览器接收指针的连续位置，输入处理代码把它们整理成点，再构造创建笔迹和追加点的操作。操作一方面送给本地场景引擎，让自己尽快看到画面；另一方面通过协作连接送到服务端，保存后再传播给其他人。其他客户端按同样的操作更新自己的场景并绘制。以后重新进入房间时，客户端还要从服务器获取已有内容，再把加载期间新到的操作合并进去。

这里有三个不能混为一谈的东西：**操作记录**描述发生了什么，**场景状态**是根据这些操作算出的当前结果，**画布像素**是当前屏幕上画出来的图像。清理画布上的像素并不会自动删除操作；收到一条操作也不代表像素已经画好。下面各阶段实际上是在逐步处理这三层之间的关系。

## S00～S03：从一次选择、编辑和撤回理解具体实现

### 基线及首次集中实现：`499474c`、`3002d84`

`499474c` 把最初反馈转成复现清单。例如选中一条曲线后，从包围盒内部的空白处按住拖动；或者先撤回两笔、画一笔新内容，再尝试重做。记录这些步骤的作用，是让“看上去不对”变成一个人可以重复的操作和可以对照的预期，详见 `docs/scene-s00-regressions.md`；它本身不修复产品。

`3002d84` 是体量最大的早期功能提交，可以拆成以下几条链路来看：

1. **选择与变换。** 原来的交互过分依赖鼠标是否落在实际笔迹上，导致包围盒内的空白和旋转控制点不能按预期操作。调整交互控制器后，先识别已有选区和控制柄，再进入拖动或旋转，而不是立刻开始一轮新框选。拖动过程使用变换预览，松手后才把最终变换作为操作提交；包围盒和内容需要使用同一套变换数据。
2. **局部画面更新。** 移动物体会同时影响旧位置和新位置：旧位置要擦去旧画面，新位置要画出新内容。改动计算受影响范围并触发重绘，避免只更新其中一边造成残影。后续的细缝修复属于同一条局部重绘链路，但问题和修复发生在 S08。
3. **撤回分支。** 撤回不是把旧操作从历史里物理删除，而是改变历史组是否生效。本地用户在撤回后新建操作，旧的重做候选就不再属于当前分支。例如画 A、B，撤回 B，再画 C：以后撤回和重做应围绕 C，不能把 B 当作 C 之后的新操作恢复。服务层维护这一关系，并结合页面及用户身份判断。
4. **线条与图形。** 绘制器增加双线对应的实际绘制逻辑；铅笔效果和图元处理调整；按 Shift 创建矩形或椭圆时，根据画布的实际宽高约束尺寸，而不是简单假定归一化坐标中的横纵单位等长，所以宽屏上也能得到正方形和正圆。
5. **文字与便签。** 文字编辑器被放到画布对应的位置，并与选区控制方式配合；字体、布局、宽度和换行需要让编辑器与最终绘制使用尽量一致的参数。文字布局涉及可保存数据，所以共享类型、服务端校验和回放也跟着调整，以便这些数据能够被接收并重新绘制。

这一提交同时包含浏览器、场景和服务端的相关用例。它把需求的主体接起来，并不意味着所有细节第一次就完全正确，后面几个提交就是继续处理具体边界。

### 后续修正：`4c2c2ac`、`90d157e`、`dd8e094`、`4f06325`、`123db79`、`46bb31c`

- `4c2c2ac`：切到曾经访问过的页面时，仅恢复已经缓存的笔迹点并不足以恢复撤回、移动、文本等状态。修复让缓存页面的场景操作也参与重放；例如画过的线被撤回后切页再切回，不能只因为原始点还在就重新显示。
- `90d157e`：文字编辑框本身已经有边框和控制点，普通选区覆盖层再画一遍就会出现重复控制点。该提交调整两种状态的交接，让同一时刻的控制界面保持一致。
- `dd8e094`：画布渲染便签时调整角部绘制，让便签的呈现更贴近编辑态，而不是编辑时圆润、提交后明显变样。
- `4f06325`：中文输入法输入时会先进入“组合输入”状态，用户确认前的内容不等于最终文字。如果编辑中断后残留该状态，下次输入可能继续套用旧组合。修正编辑中断时的状态清理。
- `123db79`：在实际走查后继续调整绘制、文字编辑和擦除的几何处理，并同步相关共享字段与服务端校验。其目的分别是让显示与编辑行为更接近、擦除区域与实际笔迹相对应，以及让这些变更能够在协作回放中使用。
- `46bb31c`：部分擦除不是把笔迹点重新改写，而是在原笔迹上记录哪些部分被遮掉。拖动预览以前没有带上这部分遮罩，于是拖动过程中缺口会暂时恢复；该提交让预览也使用擦除信息，松手前后的可见形状一致。

## S04：从断线和切页理解每次恢复改动

假设用户正在页面 A 上写字，同时网络中断；恢复时服务器既可能返回旧快照，也可能有断线期间产生的新操作。最重要的是：不要把“收到部分数据”当成“所有数据都已应用”，也不要用旧数据覆盖恢复期间刚产生的新数据。

- `24fb87a` 把恢复期间到达的实时操作保留下来，与快照合并并按操作 ID 去重。这样，另一人切页加载期间画的一笔不会因为快照后完成而被覆盖，也不会因为同时出现在快照和实时流里被算两次。
- `4a9fda0` 在恢复游标推进前等待 Worker 完成场景初始化。游标可以理解为“下次从哪里继续补数据”的书签：如果书签先往后移动，而 Worker 尚未接收完前面的内容，之后重连就可能跳过缺失部分。
- `b7467c8` 在只读房间拒绝写入时指出具体是哪次操作被拒绝。客户端才能对应处理那次本地写入，而不是只收到一个无法关联到笔迹的笼统错误。
- `07c4314` 在隔离环境记录容量诊断和运行条件。它提供一个当时的观察基线，而不是对任意设备的性能承诺。
- `0ecf053` 整理恢复边界及配套验证，把哪些状态可恢复、哪些仍有风险写进 `docs/scene-s04-reliability.md`。它的作用是使故障处理有明确范围，而非新增一个白板按钮。
- `d67304e` 校验页面恢复流是否完整；缺段或未正确结束时不宣布加载成功，避免用户看到看似正常但内容不全的页面。
- `f0cc029` 给 SQLite 的写入故障等场景增加测试，关注失败是否按预期暴露和处理，而不是只测正常保存。
- `655e677` 处理自己在页面加载时立即落笔：加载结果需要与这段时间内本地尚未确认的操作合并，不能用快照覆盖本地刚产生的内容。
- `d19f484` 对初始化流缺失和中断增加恢复处理，避免等待永远不会到来的数据或错误进入完成状态。
- `e884e3e` 遇到绘制线程异常时停止不安全的恢复流程；后续 S06 再进一步实现画布重建和未确认操作重放。待确认操作仍主要驻留内存，不能称为刷新或崩溃后必定保留的离线草稿。

## S05：从账号进入房间理解权限和会话

S05 解决的不只是登录页面：账户、房间成员、实时连接分别是不同对象。账户识别长期用户；房间成员关系记录某个账户在某个房间的角色；连接则代表某个设备当前在线的一次会话。

- `1a1956b` 增加用户名密码与账户会话，并把用于登录的用户名和展示用昵称分开。登录状态可以跨房间使用，但不等于已经加入每个房间。
- `6d845cd` 在服务端建立房间与账户的关联和成员记录，前端据此展示“我的房间”。进入允许加入的房间后形成成员关系，之后不必每次从头查找房间号。
- `6eb58e7` 加入房间配置与成员权限管理。权限必须在服务端参与判断：仅把前端画笔按钮隐藏，无法阻止有人直接发送编辑请求。
- `30b2d20` 为邀请链接增加有效期和撤销能力。链接负责提供进入入口；房间是否仍允许进入、是否需要密码仍要按房间规则检查。
- `a598f54` 加入房主身份转让和同账号设备接替。转让通过请求与接收流程处理；同账号从新设备进入同一房间时，旧连接被接替，操作归属继续关联该账号，服务于跨设备撤回自己的历史。
- `bc2a84b` 补齐游客进入、角色变化、踢出时的连接处理。游客没有稳定账户身份，因此踢出游客与对注册账户封禁的持久识别能力并不相同。
- `464b693` 把房间内切页和当前角色联动：角色或权限变化不能只更新设置面板，还要影响正在使用的白板操作。
- `891a222` 用针对性用例检查设备接替后的历史归属；`7dc93e4` 检查只读游客不能编辑。它们是验证提交，不代表增加了两种新权限。
- `5fdd457` 将房间设置入口接入白板内部，房主无需先退回房间列表才能管理；`46b7f35` 则重做入口、邀请和管理界面，并区分无状态游客和登录用户的首页内容。
- `1896feb` 调整外部测试驱动创建房间的方式，使其适应账号机制；`be84b82` 继续收紧准入流程，引入一次性 WebSocket 连接票据并调整数据库快照读取与成员处理。票据用于连接时确认身份，不应与账户的长期登录会话混为一谈。

## S06：拆分计算与绘制，逐项看接口边界

旧代码把“根据操作算出什么应当存在”和“调用 Canvas 画出来”放得比较近。`6bf8301` 将前者抽为 `SceneCore`：它管理元素、历史、空间查询和图元，不直接依赖画布；`SceneEngine` 继续作为 Canvas 适配层。这样的结果是将来替换绘制方式时不必顺带重写所有历史计算，但本次核心仍是 TypeScript。

`3523091` 引入渲染中间数据（Render IR）。可以把它理解为计算层给绘制层的一份有顺序的绘画清单：有哪些图元、位于哪里、如何显示。绘制器消费清单调用浏览器画布 API；编解码用于传递完整数据或差量，并不意味着主绘制链路已全部改为跨线程导出 JSON。

`c0efe89` 给 Worker 请求和场景生命周期增加隔离，过期回复不能更新新页面；Worker 初始化或画布转移失败时提供回退。`020426a` 分别记录消息处理、场景应用和绘制水位：这些数字帮助定位停在哪一层，但绘制命令执行不等同浏览器合成后的屏幕帧已被肉眼看到。

`5003376` 处理已经转移给 Worker 的画布发生故障：替换画布、重新同步快照并在初始化确认后重放仍在内存中的未确认操作。`9c76c4d` 提供按需获取 Worker 的完整 IR 或基于版本的差量；场景尚未就绪、版本过期或数据无效时不会假装拿到了可用结果。`a83c7a8` 保持场景修改、绘制和查询的消息顺序，并暴露队列状态，让调用方区分“已经排队”和“已经处理”。`9b0c61b` 是把 S05 已合入的改动同步到 S06 的集成提交；`2001a3e` 是 PR #28 的合并结果。

## S08：为什么要增量，分片实际做到哪里

如果白板有很多元素，而用户只在角落画了一小笔，重新扫描所有操作、重新生成所有数据、重画整张图会浪费大量工作。S08 的目标是把改动限制在受影响的部分，并把一部分大任务拆成多次执行。**分片不等于总工作量必然减少**：它主要让一次连续占用线程的时间缩短；增量处理才是避免重复计算的另一部分。

- `10801bb`：场景核心记录受影响元素及变化，供渲染数据生成差量；追加笔迹时尽量根据新图元计算脏区。Worker 合并相邻的更新，减少反复重绘，并将初始化和点批次拆成小段。历史定位和排序也避免某些全量查找。用户可能感受到大场景下更新更平稳，但这一提交本身没有证明 10 万点性能达到旧版本。
- `edd13c6`：把场景重放、排序和历史重建改为可以暂停和继续的步骤；独立的后台场景投影可在片段之间让出线程。它曾加入预测指针位置的实验，用户试用后认为收益不佳，因此后续移除。
- `e66dbfa`：删除预测功能和开关；另外修复局部重绘细白缝。局部重绘会先清除一个矩形，再查询其中可能受影响的图元并裁剪绘制。如果清除边缘落在设备像素中间，或者查询范围小于清除范围，正在画的线以及被经过的旧线都可能留下细缝。修复让清除、裁剪和查询使用一致的设备像素对齐范围；松鼠标后全量重绘能暂时抹掉缝，正是局部与全量路径结果不一致的表现。浏览器用例已覆盖这一计算方式，真实设备效果仍需走查。
- `70ba5ac`：缓存元素边界，追加新图元时更新边界，避免每次重新遍历整条长笔迹；同时将单次大笔迹创建和追加也拆段，并让独立后台投影周期性获得执行机会。
- `0feebc7`：在追加和完成笔迹时记录新增图元，按需导出差量时不必把旧的长笔迹再次整体发出。这里优化的是渲染数据导出，不应解释成网络传输总量已被实测降低到某个比例。
- `67d43b8`、`cfcc5bd`：补充维护指南与前一版总结；`557477b` 是同步 S06 主分支的集成提交。
- `d35f463`：完整绘制也可按图元顺序分批进行，在临时画布上完成后再一次替换可见画面。这样处理中途不把半张画面暴露出来；页面清空、影响整页的历史操作、初始化补充操作和完整场景同步接入分片流程。连续高亮或遮罩图元需要保持一起绘制以维持合成效果，因此某些批次仍可能较大。

同一场景正在执行的事务仍保持先后顺序：后续依赖该场景的消息要等待当前事务完成，不能把这一点描述成所有输入都能随时插队。独立后台投影与当前场景工作可以交替。没有本轮同条件基准结果，因此这里不宣称已经恢复到“十万点约 400 毫秒”。共享内存 Ring、Rust/WASM 和 WebGPU 均没有在 S08 中实现。

## 提交、合并和检查怎么对应

早期多个需求在独立分支完成后通过 cherry-pick 汇总，同一改动因此可能有两个不同提交号；上文优先使用集成分支上的编号。PR 合并提交记录代码进入主分支的节点，不应再把它当成一次独立功能开发。`bb1663a`、`7c6e413`、`7faa4b2`、`9fa0764` 则分别处理 CI 按事件分层、去掉重复 PR 检查、补充说明和验证工作流配置；它们影响检查流程，不改变白板的画笔行为。

S08 分支中的完整绘制改动执行了前端构建、局部绘制浏览器用例及提交钩子的快速测试。它们说明所运行的样例和构建通过，不等同真实设备、每一种画笔、所有多人并发场景已经验收。远端 PR 检查与用户实际试画分别是后续独立结果。

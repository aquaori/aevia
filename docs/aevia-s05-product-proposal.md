# Aevia S05 产品方案（讨论稿）

状态：待审阅。本文记录本轮已经对齐的产品规则与尚待细化的问题，不代表 S05 已开始开发。

## 1. 目标和范围

S05 在现有协作白板上加入账号、房间归属和成员管理，让用户可以长期管理自己创建或加入的房间，同时保留游客快速协作的方式。原排期中的快照发送与慢客户端隔离也属于 S05 的工程范围。

界面应延续 Aevia 现有的视觉风格和操作习惯：浅色背景、半透明白色界面、靛紫色强调色、圆角和轻量浮层。登录、房间列表和房间设置等新增界面应与现有首页、邀请页和白板一致，而不是另起一套产品风格。后续设计和实现使用用户指定的 frontend-design、ui-ux-pro-max 和 hallmark；当其通用审美建议与现有产品风格冲突时，以延续 Aevia 的风格为准。

## 2. 账号与用户身份

- S05 实现用户名、密码注册与登录；设计时为未来接入邮箱和第三方登录留出扩展空间，但本期不实现这些登录方式。
- 用户名用于登录；显示昵称与用户名分开，昵称可修改。
- 默认保持登录，直到用户主动退出或会话过期。允许同一账号同时登录多个浏览器或设备；退出当前设备不影响其他设备的账号登录。
- 第一版暂不提供忘记密码的自助找回。未来可在接入邮箱等可验证方式后补充。
- 登录后的首页展示“我的房间”，并保留创建房间和加入房间入口。
- 创建及管理普通房间需要登录。未登录用户可按房间规则以游客身份进入已有房间。

## 3. 房间与成员

### 3.1 房间角色

S05 设三种角色：房主、编辑者、只读者，暂不设置管理员。

| 身份或角色 | 已确认的能力和边界 |
| --- | --- |
| 房主 | 管理房间信息、密码、加入规则、成员和角色；可踢出、封禁；可发起房主转让；可删除房间。 |
| 编辑者 | 可以编辑白板、生成和撤销邀请链接。游客编辑者与注册编辑者具有相同的分享权限。 |
| 只读者 | 以只读身份访问白板；不能进行白板编辑。 |
| 游客 | 无需注册，可按房主设置进入；默认可编辑，房主可以调整为只读。游客不是持久注册成员。 |

房间需要可配置新成员的默认角色，初始值为编辑者。已登录用户第一次进入后自动成为长期成员，可在“我的房间”中再次进入；房主可以调整单个成员的角色。注册成员可主动退出成员关系，退出后房间从其列表移除，在房间规则允许时可重新加入。

### 3.2 加入方式与密码

- 加入入口包括房间号和邀请链接。房主可关闭房间号加入。
- 房主可以分别控制游客是否可以通过房间号、邀请链接进入；新建房间时两项默认都允许。
- 房主可设置或修改房间密码。房间设置了密码时，尚需验证密码的访客通过邀请链接进入也必须输入密码；邀请链接本身不绕过密码。
- 已加入的长期成员不受关闭房间号加入的影响。
- 房主修改密码时，可以选择要求所有人下次进入时重新输入密码，该选项默认关闭；未选择时，已有长期成员不因修改密码而必须重新验证。
- 登录用户、游客和已加入成员在不同设置下的具体页面提示应清晰表达实际进入条件。

### 3.3 邀请链接

- 邀请链接可以重复使用，支持设置有效期和手动撤销。
- 房主和编辑者均可以生成和撤销邀请链接；游客编辑者也有相同分享权限，只读者没有上述分享权限。
- 链接只提供进入房间的入口，不绕过房间密码、游客入口开关或封禁规则。

### 3.4 踢出、封禁和游客限制

- 房主可以踢出注册成员，也可以封禁注册成员。被踢出后，如果房间规则允许，成员可以重新加入；被封禁后不能加入，直到房主解除封禁。
- 游客没有稳定账号身份。踢出游客时，界面应说明无法永久禁止其再次进入，并引导房主按需要关闭游客进入、设置或修改房间密码。
- 密码已被该游客知晓时，仅保留原密码不能阻止其再次进入；界面提示应避免给房主造成永久封禁游客的误解。

### 3.5 房主转让与删除

- 房主可向其他**已注册成员**发起房主转让；接收方确认后才生效。
- 可以向离线成员发起；请求保留到对方下次登录后处理。
- 转让完成后，原房主成为该房间“新成员默认角色”对应的角色；确认转让前须明确提示原房主将获得的角色。
- 房主可修改房间信息、密码和加入规则。房主确认删除房间后，永久删除房间及白板内容，所有成员失去访问权限。

## 4. 多端、操作归属与历史

- 同一账号可以多端登录，但不能同时在多端进入**同一个房间**。后进入的设备挤掉先进入的设备。
- 接替进入的设备应继承该账号在该房间此前的撤回与重做资格，包括此前仍然有效的重做分支；不能因为换设备而让这些操作变成不可撤回。
- 每个人只能撤回、重做自己的操作，房主也不例外。
- 游客在房间中画过内容后登录账号时，原游客笔迹保留，但不自动转归账号；登录后的新操作属于账号。
- 不同账号、游客会话与同一账号的不同设备，应有清晰的操作身份边界；不能仅凭可修改的显示昵称决定历史归属。

## 5. 旧房间与系统默认房间

- 产品尚未有正式用户，除系统默认房间外，其他旧房间不要求兼容或迁移。是否在部署时清空数据库，由部署时另行决定；开发过程不自动清空现有数据库。
- `123123` 在非生产环境默认保留，所有人可直接进入并编辑。
- 生产环境默认不创建、不保留 `123123`，以免占用房间号。

## 6. 建议实施拆分

下列顺序是用于审阅的工作拆分，不代表已授权开始开发；具体依赖和估算需在方案确认后结合代码进一步确定。

1. **账号与会话**：用户名密码、账号会话、多端登录、独立昵称和基本账号入口。
2. **房间归属与列表**：创建房间归属、我的房间、加入及主动退出；处理非生产默认房间。
3. **准入、角色和成员管理**：两类游客入口、房间号开关、密码、新成员默认角色、成员角色、踢出和封禁。
4. **邀请链接**：生成、有效期、重复使用、撤销，以及与密码、游客和角色规则的组合。
5. **房主转让与删除**：持久转让请求、接收方确认、离线接收和原房主降级；删除房间及内容。
6. **同房间多端接替与历史继承**：同账号连接互斥、旧端提示、操作身份及跨设备撤回/重做恢复；处理游客登录后的身份边界。
7. **快照发送和慢客户端隔离**：在现有 Go 后端上处理快照期间房间交互和慢客户端影响，作为工程工作独立实施。
8. **界面与组合验收**：贯穿上述工作包，沿用现有风格；优先验证各功能主链路及关键权限边界，不追求穷举所有组合。

每个需求在独立开发分支完成并推送，再汇集到主开发分支；集中验收后按既定流程准备 PR。提交和 PR 使用中文说明。S05 的开发基线及是否合并此前 PR，应在实际开始前结合当时的分支状态处理。

## 7. 尚待细化的实现与交互问题

以下不是本轮已经确定的产品结论；实现方案应先提出合理默认并在必要时与用户确认：

- 邀请链接的默认有效期、可选时长、链接列表呈现，以及允许同时存在多少条有效链接。
- 房主转让请求是否支持撤销、拒绝、过期，以及重复请求如何呈现。
- 用户名与密码的具体格式规则、会话有效期，以及账户昵称修改的界面位置。
- 被踢出或封禁的账号此前创建的笔迹继续保留时，成员列表、历史和再次加入后的展示细节。
- 游客从房间内登录时的具体交互，以及未完成的编辑动作如何结束；不改变第 4 节已确认的操作归属规则。
- 不同设备接替时正在进行、但尚未收到服务端确认的操作如何提示；已确认历史的撤回/重做接续属于明确要求。
- 房主删除房间或成员权限变化时，当前在线客户端的提示和退出时序。
- 非生产默认房间的开关与具体初始化机制，以及生产环境中旧默认房间的部署处理方式。
- 快照异步执行的具体技术边界、资源限制和降级方式，应以现有实现及实际需求为依据。

## 8. 验收重点

- 注册、登录、保持登录、退出及昵称修改可完成主要使用流程。
- 注册用户创建、加入、退出和再次进入房间符合上述规则；游客的两类入口、房间密码和邀请有效性符合房主设置。
- 各角色的白板编辑、邀请、成员管理能力符合规则；权限变化不仅改变界面，也在服务端生效。
- 房主转让需要接收方确认；离线请求可在下次登录后处理；转让前提示原房主的后续角色。
- 踢出、封禁、游客限制提示及永久删除房间符合已确认的行为。
- 同一账号同一房间多端接替时旧端退出；新端继承该账号有效的撤回、重做资格，不能操作其他人的历史。
- 游客登录后，旧游客操作保留且不自动归入账号。
- 界面延续现有产品风格；相关检查聚焦功能主链路、身份和权限边界，遗留场景如实记录。
